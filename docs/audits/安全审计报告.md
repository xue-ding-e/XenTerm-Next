## 1. 执行摘要

MeatShell Next 是凭据密集型桌面客户端：它在本机保存 SSH 密码、内联私钥与代理口令，并把它们送到远端主机。**本机配置文件、传输链路、远端对端**因此构成三个核心信任边界，本次审计围绕这三处展开。

### 1.1 总体评价：工程质量高于同类项目

以下关键设计经逐行核对确认正确（完整清单见 §6 I-06）：

- 主机密钥采用 TOFU + 首连确认，**无 UI 时一律 fail-closed**（`src/ssh/impls/ssh.rs:2831-2842`；自动化路径显式 `respond(false)`）；
- PPK 私钥解析对文件大小、Argon2 参数设上限，**先解密、再对明文验 HMAC，验签通过后才把密钥交给 `ssh-key` 解析**，全程 `Zeroizing`，转换结果不落盘；
- SFTP 落地文件名有统一净化（含 Windows 保留设备名、ADS、控制字符），远端命令拼接**全部**经 `sh_quote`，旧的 `cmd /C start` 参数注入已改为直接 `ShellExecuteW`；
- 服务端可控数据的解析普遍使用 `saturating_*` 与长度/条目上限；全仓 `unsafe` 仅 5 处且集中在 Win32 FFI；
- MCP / 自动化输出走白名单结构（`safe_session` 只回布尔标志，绝不回密码）；
- 全仓**未发现**把口令、passphrase、私钥内容或 `secret.key` 字节写入日志的代码路径。

### 1.2 但存在若干“策略与实现不一致”，且集中在新增能力面

1. **MCP 与插件是风险最集中的区域。** MCP 的四个权限开关对**既有配置**的 serde 默认值是 `true`（`src/config/struct/config_file.rs:21-25,278-289`，代码注释本身就写着“稳定版前要改成 false”）；一旦用户按正常方式接入任意 MCP 客户端，该客户端即可对**全部已保存会话**执行任意命令并读写本机文件，且没有二次确认。插件的“授权 = 申请 ∩ 用户决定”模型逻辑上相当严谨（`src/plugin/impls/grants.rs:46-56`），但**授权记录与解密密钥 `secret.key` 就放在插件进程可读写的同一目录里**，插件进程又没有任何沙箱（全仓无 job object / seccomp / AppContainer / `env_clear`），于是该模型在真实攻击面前失效。
2. **凭据的“等价明文”存储。** 会话密码与内联私钥确实用 ChaCha20-Poly1305 加密了，但 (a) 本地密钥 `secret.key` 与密文同目录同权限；(b) **导出 / WebDAV 同步用的是一枚编译进二进制的固定密钥** `EXPORT_KEY`（`src/config/impls/config.rs:397-399`），拿到导出文件即等于拿到全部凭据的明文；(c) 代理口令走的是**完全未加密**的 `Session.proxy` 字符串。
3. **远端可控数据触达本地文件系统。** ZMODEM 接收可由远端输出单方面触发、无任何用户确认，直接向用户 Downloads 目录写文件并静默截断同名文件；SFTP 下载完全信任远端 `stat` 声明的大小。
4. **TLS/证书策略被一个全局开关替代。** WebDAV 的“信任自签名证书”实现为**全盘接受任意证书、且不校验握手签名**（`src/webdav/impls/certificate_verifier.rs:3-38`），而应用自身的错误提示会引导用户去打开它。
5. **对端可单方面获取本机提交的凭据。** sudo 口令的投递条件是“远端输出含 `password`/`密码` 子串”或“3 秒静默”（`src/ssh/impls/ssh.rs:748-752,829-832,694-703`）；会话触发器的自动应答会把保存的 Secret 交给任何打印出匹配字符串的对端。

**建议处置顺序见 §7。** 其中 P0 的六项均可在 1–3 天内以较小改动完成，并可消除风险最高的几条路径。

## 3. 高危发现

### H-01 主机密钥“已变更”告警可在同一运行期内被静默吞掉（TOFU 失效）

- **等级**：高 ｜ **CWE**：CWE-295、CWE-863
- **位置**：`src/session/impls/prompt_queue.rs:158-172`，配合 `src/ssh/impls/ssh.rs:2834-2840`
- **证据（已逐行复核）**：

```rust
// src/session/impls/prompt_queue.rs:158-162
let id = format!("{host}:{port}");
if let Some(accepted) = HOSTKEY_DECIDED.with(|d| d.borrow().get(&id).copied()) {
    responder.respond(accepted);
    return PromptOutcome::AlreadyDecided;
}
// :166-169 —— 合并只比对 host+port，不比对指纹
if let Some(pending) = q.iter_mut()
    .find(|p| p.window_id == window_id && p.host == host && p.port == port)
```

- **问题**：决策缓存的键是 `host:port`，**不含 `key_type` 与 `fingerprint`，也不参与 `changed` 判断**；命中缓存即在查看 `changed` 之前直接以“已决定”回真值。因此同一进程运行期内，某 `host:port` 被接受过一次之后，后续针对它的**任何**提示——包括 `HostKeyStatus::Changed`（“密钥变了，可能是中间人攻击”这一唯一告警）——都会被自动回答“信任”；随后 `verify_host_key` 调用 `known_hosts::remember` 把**攻击者的密钥覆盖写入**信任库（`src/ssh/impls/ssh.rs:2834-2840`）。第 168 行的合并逻辑同样只按 host+port 合并，使一次确认可覆盖不同指纹的多条并发连接（典型场景：直连与经跳板机同时发起）。
- **攻击路径 / 前置条件**：同一次运行内，用户先正常接受过该主机的密钥 → 攻击者在 DNS/路由/代理/跳板机层面呈现另一把密钥 → 提示被自动放行，无任何 UI 输出，新密钥被持久化。
- **影响**：`known_hosts` 的 TOFU 安全属性被破坏；攻击者一旦取得一次网络位置，即可把该主机永久“中间人化”而用户端完全静默。
- **修复状态：已修复。** 改动落在 `src/session/impls/prompt_queue.rs`、`src/session/struct/prompts.rs`：
  1. 新增 `decided_id(host, port, key_type, fingerprint)` 作为运行期决策记忆的键（地址 **+ 密钥**，而非仅地址）；
  2. `enqueue_host_key` 在 `changed == true` 时**完全不查记忆**，并且同一地址但**不同密钥**的提示不再合并进同一个对话框；
  3. `resolve_host_key` 仅在 `accept && !changed` 时写入记忆——接受一次“已变更密钥”不再构成对该密钥的长期许可；
  4. `PendingHostKey` 增加 `key_type` / `fingerprint` 字段（记忆键与合并规则都需要）。
  回归测试：`an_accepted_key_does_not_vouch_for_another_key_at_the_same_address`、`a_changed_key_asks_every_time_even_after_this_run_accepted_the_host`。
  验证：`cargo check --bin xenterm` 通过（无新增告警）；`cargo test --bin xenterm -- prompt_queue` → **9 passed / 0 failed**（含 7 个既有测试，无回归）。
- **修复建议**（原始建议，保留供对照）：
  1. 缓存键改为 `format!("{host}:{port}:{key_type}:{fingerprint}")`；
  2. `changed == true` 时必须每次弹窗，禁止命中缓存：

```rust
let id = format!("{host}:{port}:{key_type}:{fingerprint}");
if !changed {
    if let Some(accepted) = HOSTKEY_DECIDED.with(|d| d.borrow().get(&id).copied()) {
        responder.respond(accepted);
        return PromptOutcome::AlreadyDecided;
    }
}
```

  3. 第 168 行合并条件加入 `key_type` + `fingerprint`，保证一个对话框只代表一把密钥；
  4. “密钥变更”建议单独设计更醒目的 UI（红色告警、需手动输入主机名确认），不复用首连对话框。

- **等级**：高 ｜ **CWE**：CWE-321、CWE-312
- **位置**：`src/config/impls/config.rs:397-399`、`1727-1755`、`1760-1794`；使用点 `src/app.rs:1236-1244`（WebDAV 上传）、`src/gpui_app/impls/shell.rs:2821`

- **问题**：`EXPORT_KEY` 是源码中的公开常量，任何拿到导出文件的人都能**离线**解密其中的全部密码、**整把内联私钥**与自动应答内容；其余字段（主机名、端口、用户名、分组、跳板关系、`proxy`、`private_key_path`）本就是明文。代码注释承认这“只是混淆”，但该文件的实际使用场景（导出/导入、WebDAV 同步到 NAS 或云端）恰是最易泄露的场景。补充：`export_to`（`:1790-1794`）用 `fs::write` 写文件，**不设置 0600**（Unix 下通常是 0644），与 `sessions.json` 的 0600 不一致。
- **攻击路径 / 前置条件**：导出文件泄露（邮件/群聊/U 盘/云同步/备份/WebDAV 服务端运维/共享目录），或与 H-03/M-06 组合被网络中的攻击者获取（WebDAV 允许 `http://` 明文传输该文件）。
- **影响**：一次文件泄露 = 该用户全部 SSH 凭据泄露，且无需接触用户本机。
- **修复建议**：
  1. 导出时要求用户设置**导出口令**，用 Argon2id（或 PBKDF2-HMAC-SHA256 ≥ 600k 迭代）派生密钥后加密，头部保存 KDF 参数与随机盐；用新前缀 `enc:exp:v2:` 兼容旧文件（旧前缀仍按 `EXPORT_KEY` 解，但导入时提示“旧格式，弱保护”）；
  2. 若必须保留无口令导出：默认**不导出**密码与内联私钥，仅在用户明确勾选时导出，并在 UI/文档标注“该文件包含可被解密的凭据”；
  3. WebDAV 同步不要复用便携导出格式，改用会话密钥（或用户口令派生的密钥）加密后再上传；
  4. `export_to` 改为 `OpenOptions::new().write(true).create(true).truncate(true)` + `#[cfg(unix)] OpenOptionsExt::mode(0o600)`；
  5. 长期方案：口令入 OS 凭据库（DPAPI / Keychain / libsecret），`sessions.json` 只存引用。

> **与 H-03 / M-06 的组合链（务必一并修复）**：WebDAV 允许 `http://` 明文地址（`src/app/webdav.rs:5-13`）+ 上传内容为固定密钥加密的导出文件 → 同网段攻击者抓到一个 PUT 请求即可离线解密全部凭据。

### H-03 WebDAV「信任自签名证书」等价于完全关闭证书校验与握手签名校验

- **等级**：高（需用户开启该开关，但应用自身的错误提示会引导用户开启）｜ **CWE**：CWE-295、CWE-306

- **可达性判定（已确认）**：该验证器**仅在配置项 `webdav_accept_invalid_certs == true` 时安装**，其 serde 默认为 `false`，UI 标注为“信任自签名/内网证书”。因此**不是默认行为**。但三点使其仍属高危：
  1. 它是**全局布尔、不绑定主机/指纹**：开启一次后对配置中的**任意 URL**都接受任意证书，且不检查有效期；
  2. 应用在证书错误时主动提示用户去打开它（`src/app/webdav.rs:139-146`：“HTTPS 证书不受信任；如果这是可信 NAS/局域网 WebDAV，请在设置里开启…”，`:19,:28` 甚至直接建议 `http://...:5005`），把不安全选项变成“官方推荐操作”；
  3. `verify_tls12_signature` / `verify_tls13_signature` 也一并被断言为合法，**连签名证明都不再校验**。
- **攻击路径 / 前置条件**：用户为该开关开启（为自签名 NAS，或开过忘记关闭、之后改用公网地址）→ 同网段/路径上的攻击者（ARP/DNS/恶意热点/上游代理）出示任意证书即可 MITM → 读到 `Authorization: Basic`（WebDAV 账号口令）与 PUT 请求体（H-02 的导出文件，可离线解密为全部会话凭据）；下载方向还可返回构造 JSON，经 `import_json` 注入新会话（含 `forwards[].bind_addr = "0.0.0.0"`、指向攻击者主机的 `host`、自动应答 `triggers`）。
- **影响**：全部已保存 SSH 凭据泄露，或经同步注入把用户引向攻击者主机并自动开启非回环隧道。
- **修复建议**：
  1. 用**证书固定**替代“全盘接受”：首次连接展示 SHA-256 指纹，用户确认后按 `主机:端口 → 指纹` 记录（可复用 `known_hosts` 模式），之后仅接受该指纹，变更时报警；
  2. 无论如何都保留 `verify_tls12_signature` / `verify_tls13_signature` 的默认实现（不要 `assertion()`）；

- **等级**：低 ｜ **CWE**：CWE-316、CWE-532 ｜ **位置**：`src/config/impls/finalshell.rs:141-156`、`:22-33`
- **问题**：解密后的明文 `Vec<u8>` 与 GBK 回退字符串都不清零；`#[derive(Debug)] struct FinalShellConnection`（含 `password: String`）会打印文件中的 Base64 密文。当前该结构体模块私有且无日志点，属潜在风险。已核对：DES/MD5 在全 `src` 中**只**出现在 `finalshell.rs`（仅用于解析历史导出），解密结果立即包成 `Secret`，错误上下文只带 host，`remove_pkcs5_padding` 校验正确，`derive_des_key` 对除零与长度有保护。
- **修复建议**：用 `Zeroizing::new(ciphertext.to_vec())` 并显式清零；去掉 `#[derive(Debug)]` 或手写 `Debug`（password 打 `***`）。

### L-20 会话事件通道无界 + 每轮批量上限 → 远端洪流可无界积压

- **等级**：低 ｜ **CWE**：CWE-770、CWE-400 ｜ **位置**：`src/ssh/impls/ssh.rs:902-903`、`src/app/session_runtime.rs:160-166,289-293`
- **问题**：读取侧（SSH 任务）与消费侧（每标签页 pump 线程，做 vt100 ingest + 触发器扫描 + 可选 JSON 美化）之间只有一个 `unbounded_channel`；pump 每轮最多取 2048 个事件。当远端输出速率超过本地 ingest 速率（启用 `json_format_output`/`output_highlight`/触发器时明显降低）时，未消费事件无界堆积，内存 1:1 于未处理字节；代码注释明确承认这是 “intentionally unbounded”。
- **修复建议**：事件通道改为有界 `mpsc::channel::<SessionEvent>(N)` 并在读取侧 `send(..).await` 形成背压；或在会话任务里对 `Output` 做累计字节限额合并（待发超过 1 MiB 即等待 pump 结算）。

### L-21 解密失败被静默忽略：密文会被当作口令保存并使用

- **等级**：低 ｜ **CWE**：CWE-390 ｜ **位置**：`src/config/impls/config.rs:423-434,501-506,1821-1826`
- **问题**：`try_decrypt` 对“非 `enc:v1:` 前缀”与“解密/认证失败”都返回 `None`，两种语义被合并。当 `secret.key` 被替换/损坏/长度不为 32（`:454` 只 warn 后重新生成）或 `sessions.json` 被篡改时，内存里留下字面量 `enc:v1:…`，它会被 `resolve_credentials`（`src/ssh/impls/ssh.rs:2857`）取用并发往服务器，同时因前缀匹配而在 `save()` 中被跳过重加密，原样存回磁盘，用户无任何提示。
- **影响**：非凭据泄露（发出的是本机密文，无密钥无用），是可用性/正确性缺陷：用户看到莫名“认证失败”，配置进入难以自愈状态。
- **修复建议**：`try_decrypt` 改三态（`Plain` / `Encrypted` / `Undecryptable`），后者清空口令、标记需重填并提示“密码无法解密（secret.key 已更换？）”；在 `resolve_credentials` 与 `load_session_private_key` 入口拒绝任何以 `ENC_PREFIX`/`EXPORT_PREFIX` 开头的值。

## 6. 信息级发现与已核实结论

### I-01 RUSTSEC-2026-0154 的忽略结论可接受，但缺少 CI 兜底

`audit.toml:22` 忽略 `RUSTSEC-2026-0154`（russh SSH-AGENT 帧解析的无界分配 DoS），理由是该程序从不使用 ssh-agent。经全仓核对：**未发现任何 ssh-agent 使用**（无 `SSH_AUTH_SOCK`、无 agent 客户端代码，`russh 0.49.2` 的相关路径不可达），结论成立（`Cargo.lock` 中 russh/russh-keys 均为 0.49.2）。但仓库**没有任何 CI 步骤运行 `cargo audit`/`cargo deny`**，也没有依赖更新机器人配置，忽略项会随时间静默累积。建议在 CI 增加 `cargo audit --deny warnings`（保留 `audit.toml` 的忽略项并加注释）并接入 Dependabot。

### I-02 Flatpak 打包权限过宽

`packaging/flatpak/io.github.yituorou.meatshell.yml:8-19` 申请 `--filesystem=home`（注释已说明原因：文件传输与本地终端尚未全面走 portal）与 `--device=all`（注释说明是为串口会话）。`--device=all` 会同时暴露输入设备等无关设备，削弱沙箱。建议在串口会话改用 portal 后收窄为 `--device=dri` + 具体串口设备节点。

### I-03 keyboard-interactive 会把存储口令回填给第一个“看起来不像 MFA”的提示

`src/ssh/impls/ssh.rs:2748-2765`：对首个非 MFA 提示直接回填存储口令。该对端已完成主机密钥校验（`check_server_key` 在认证前执行），因此这只是“服务器可自定提示文案”的固有特性，不是独立漏洞；但建议在提示文案与预期不符时（例如要求“输入新密码”）不要自动回填，改为询问用户。

### I-04 `mcp_enabled` 关闭时 `initialize` / `tools/list` 仍会应答

`src/mcp/impls/server.rs:47-53` 不经过 `load_store`，因此关闭 MCP 后仍会响应 `initialize` 与 `tools/list`（仅泄露工具名与版本号），`tools/call` 才被拒绝。属极小信息问题，修复 H-04 时一并处理即可。

### I-06 已核实为**无问题**的安全设计（正面确认）

1. **主机密钥校验 fail-closed**：无 UI 时拒绝连接（`ssh.rs:2831-2833,2841`）；`check_server_key` 直接返回校验结果（`ssh.rs:2923-2928`）；SFTP 复用同一函数（`sftp.rs:2321-2329`）；信任库格式为自有的 `host:port <openssh 单行密钥>`，与 `~/.ssh/known_hosts` 隔离（`known_hosts.rs:11-13`），OpenSSH 的哈希条目只会导致“未知主机”弹窗（fail-safe）；拒绝不会被缓存为全局拒绝（`prompt_queue.rs:36-39` 的注释与实现）。
2. **PPK 解析**：文件大小上限 16 MiB；行数上限；`WireReader` 用 `checked_add` + `get()`；**先解密、再对明文 blob 验 HMAC，验签通过后才 `ppk_to_openssh`**（`:58-60`），未认证的密钥材料不会被使用；转换结果经 `PrivateKey::from_bytes` 校验且需公私算法一致；不落盘。仅存的缺陷是 L-01 与 M-16。
3. **SFTP 路径安全**：远端名统一经 `sanitize_filename` + `base_name`（`sftp.rs:672-677,760,1246-1253,1623-1625,1751-1752,2063-2076`），覆盖 `..`、绝对路径、UNC、ADS、Windows 保留设备名与控制字符；远端命令拼接**全部**经 `sh_quote`（仅两处构造点 `sftp.rs:778-783,796`）；旧的 `cmd /C start "" <path>` 参数注入已改为直接 `ShellExecuteW`（`sftp.rs:1506-1548`），Unix 侧 `xdg-open` 为单 argv 且传绝对路径；本地符号链接跟随无可利用点（下载目录树由客户端新建）。
4. **凭据处理**：`Secret` 类型 `zeroize` + 脱敏 `Debug`；`ProxyConfig` 的 `Debug` 亦脱敏；`secret.key` 用 `OsRng`（256 bit）；ChaCha20-Poly1305 每个值随机 nonce；`sessions.json` 经临时文件 + `0o600` + `rename` 原子落盘；全仓未发现把口令/私钥写进 `tracing` 的语句；MCP/自动化输出用白名单 `safe_session`（`tools.rs:248-264`）。
5. **远端命令与脚本**：监控/系统信息脚本为常量且显式重置 PATH（`ssh.rs:1612-1616`）；本地 shell/WSL 启动参数为固定字符串、无插值（`local.rs:19-21,230-320`）；`execute_command` 的输出有 4 MiB 上限、超时 300 s 上限（`tools.rs:10-13`）。
6. **内存与解析**：`unsafe` 仅 5 处集中在 Win32 FFI（`app.rs:3154,3466`、`app/window.rs:45`、`app/jump_list.rs:60,66`、`sftp.rs:1538`、`terminal/impls/input.rs:345`）；服务端监控数据解析使用 `saturating_*` 与条目数上限（`ssh.rs:2297-2400`）；`automation/impls/sftp.rs:51-64,113-126,185-198` 对 HostKey/Credential/MFA 一律拒绝应答。
7. **未接线的高风险终端特性**：未发现 OSC 52（远端写本地剪贴板）的处理路径（`vt100 0.15.2` 的剪贴板回调未被使用；其 `osc_dispatch` 只处理 OSC 0/1/2），也未发现 OSC 8 超链接被本地打开；剪贴板读写均由用户操作触发；`app.rs:2284-2312` 打开 URL/目录只接受硬编码 release/repo URL 与本地设置目录，不接受远端文本。

### I-07 `Secret` 的字段是 `pub(crate)`，遮蔽 `Debug` 可被同 crate 代码绕过（当前无绕过点）

`src/config/struct/secret.rs:10` 的 `pub struct Secret(pub(crate) String)`：遮蔽只覆盖 `Debug` 与 `Drop`，crate 内任何代码都能 `secret.0` 取明文并落进日志。按 `password.0`、`.as_str()` 与 `tracing::*` 组合全 `src` 搜索**未发现实际绕过点**（`as_str()` 只用于加密/比较/认证）。建议改为私有字段 + 显式的 `pub(crate) fn expose(&self) -> &str`，便于审计与 grep。

### I-08 CLI 帮助文本与实现的一致性（附带观察）

`src/cli/impls/cli.rs:403-406` 声明“MeatShell starts a process only for a plugin it has granted something to”，但 L-05 的 `cli plugin` 路径不满足该承诺；L-13 的 `--` 语义也未在帮助中说明。建议在修复上述两条时同步更新帮助文本。
