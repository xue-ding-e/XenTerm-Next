## 为什么不能点一个 PR 的 Rebase and merge 来替换历史

GitHub 的普通 Merge、Squash and merge、Rebase and merge 都是在目标分支当前历史上合入贡献，不负责把目标分支已存在的祖先替换成另一套历史。整理已有 main 需要管理员在协调窗口内做精确 ref 切换。候选可以供管理员查看、下载和验证；不能把一个普通 PR 的合并按钮描述成全历史 force 功能。

官方说明：
- https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github
- https://git-scm.com/docs/git-push
- https://git-scm.com/docs/git-commit-tree

## 无需私有附件的公开准备方式

管理员可从 fork 的 `history/linear-admin-final-v2-20261012` 维护交付分支获取脚本，按其中 README 运行 `prepare_admin.py`，直接从公开仓库及原 beta 资产准备新的完整离线备份。该过程核验固定 main/tag/candidate SHA、逐快照 tree 和完整映射，不更改远端；任何状态变化均停止。准备后的精确 plan 只更新刚刚完整备份的文件校验值，不改变目标 ref 的预期旧 SHA。用户的 Library 附件是额外离线恢复副本，无需给管理员私有 Library 权限。

## 管理员最短执行路线

依赖 Git、Python 3.10+、curl、已经正常登录且有目标仓库写入权限的 GitHub CLI。无需在文档或聊天里填写 token。Windows 可以用 PowerShell；macOS / Linux 用终端。Python 命令按本机实际安装选择 `python` 或 `python3`。

1. 将核心迁移包以及资产备份 A、B 三个 ZIP 解压到同一个目录，核验 SHA256SUMS；完整备份资产必须在该目录的 `release-assets/`。不要只下载单个脚本。
2. 协调所有提交者暂停写入，取得管理员批准的发布冻结；管理员自行在 GitHub 关闭 Release workflow 并确认已运行的发布任务全部结束。脚本不会修改任何权限/设置、不会替管理员关闭工作流。也不要用 `[skip ci]` 代替可靠冻结。
3. 在本目录建立隔离执行仓库，一次执行：

```sh
git clone --mirror upstream-before.bundle migration.git
git -C migration.git fetch ../linear-candidate.bundle refs/heads/history/linear-main-20261012:refs/heads/history/linear-main-20261012
```

4. 一条只读预检查：

```sh
python admin_apply.py --git-dir migration.git
```

5. 所有检查通过、管理员确认变更窗口和发布影响后，一条显式执行：

```sh
python admin_apply.py --git-dir migration.git --execute --confirm-repository ixbaicn/XenTerm --acknowledge-history-rewrite --acknowledge-release-impact
```

该步骤只更新审阅计划中的上游 `refs/heads/main` 与 `refs/tags/beta`。使用 atomic push 与每个 ref 的精确 `--force-with-lease=ref:旧SHA`，不会使用裸 force 或 push --mirror。上游任何 heads/tags 与快照不同会拒绝；不得为了通过检查直接改 expected SHA，必须重做备份、候选和影响核验。

6. 出现需要回滚的情况且远端没有后续新增工作，一条回滚预检查或显式执行：

```sh
python admin_apply.py --git-dir migration.git --rollback
python admin_apply.py --git-dir migration.git --rollback --execute --confirm-repository ixbaicn/XenTerm --acknowledge-history-rewrite --acknowledge-release-impact
```

回滚要求本次执行生成的 `cutover-receipt.json` 与原计划一致，且远端仍是切换后的精确状态。它不会覆盖其他人切换后新增提交，也不会自动恢复 Release 网页/资产；这些必须按资产备份和元数据单独恢复。

- fork-plan.template.json 是完整清单的公开模板，唯一自身 SHA/tree 占位由固定交付提交确定；prepare_admin.py 输出可执行 fork-plan.json，没有待定功能 SHA。82 个旧分支在完整 bundle 验证、精确 lease、开放 PR head/base 保护及协作冻结确认后才允许归档删除。剩余 refs 必须两两存在祖先关系，且零 merge，否则拒绝。
- fork_apply.py 默认只读；显式执行使用 atomic、--no-follow-tags 和每个 ref 的精确 lease。每个旧 ref 都必须在绑定 SHA256 的 fork bundle 中存在，成功后保存回执；rollback 使用回执恢复旧 refs，包括精确不存在才恢复已删除分支。
- 纯主线候选与未批准产品功能保持各自审核点；线性结构不代表自动批准或合入所有产品功能。
- 跨仓库不能作为一笔 Git 原子事务切换；上游 main/tag、fork 工作分支和 PR base 必须在协调冻结窗口分阶段执行并分别验证。
- GitHub 的历史 `refs/pull/*` 由平台管理，不是普通可写分支；旧 PR 页面、旧对象链接不保证消失。GUI 只查看新的 heads/tags 会呈现新线；主动获取旧 pull refs 或重新推回旧归档会再次显示旧图。

## 恢复与备份文件

- `upstream-before.bundle`：原上游完整 Git 对象与 refs
- `fork-before.bundle`：最终交付快照 fork 的完整 Git 对象与全部 refs，包括原 84 分支及新候选/规范分支
- `linear-candidate.bundle`：新主线候选的完整历史
- `beta-release-full.json`、`beta-release.json`、`release-assets/`、`release-assets-verified.json`：原 beta 元数据、下载制品和逐个校验值
- `upstream-plan.json`：只更新上游 main / beta 的精确计划
- `fork-ref-audit.json`：旧 fork refs 分类，不自动授权删除

原始对象、映射和备份应离线保存，避免在开发仓库的 heads/tags 中保留旧分叉。迁移后协作者优先重新 clone；有未提交或未推送工作的协作者先备份并逐项迁移，不能要求其直接 reset 丢弃工作。

完整 fork 阶段的预检、显式执行和回滚命令见同目录 README。上游与 fork 写权限可能属于不同人员，必须分别由有权限的操作者执行；两个仓库之间不能承诺原子切换。
